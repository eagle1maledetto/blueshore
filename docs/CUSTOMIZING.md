# Customising Blueshore

Blueshore is built from one shared source and a palette file per variant.
Everything that changes between variants is a colour token in
`skin.properties`; `skin.css` and the icon generator contain no colour
literals.

```
src/blueshore/skin.properties   design tokens (tide values) + core skin settings
src/blueshore/skin.css          layout and component styles, token references only
src/blueshore/blueshore.js      skin-local enhancements (see below)
palettes/<name>.properties      SkinName + tokens that differ from src
tools/build.py                  palette -> skins/<SkinName>/
tools/gen-icons.py              skin.properties -> icons.css + img/images.css.js
tools/lucide/                   vendored Lucide SVG subset (ISC)
```

Never edit `skins/`: it is regenerated by the build and not tracked in git.

## Building

```sh
python3 tools/build.py tide            # one variant  -> skins/blueshoretide/
python3 tools/build.py tide sanddark   # several
python3 tools/build.py --all           # every palettes/*.properties
```

Python 3.8 or newer, standard library only. For each palette the build copies
`src/blueshore/` to `skins/<SkinName>/`, merges the palette tokens into
`skin.properties`, then runs `gen-icons.py` on the result so that the icons
take the variant's colours. A palette token that does not exist in the source
is an error (typos cannot slip through), and so are lines that are not
`Name = value`, names defined twice, and colours used by the icon generator
that are not plain `#rgb`/`#rrggbb` (they are embedded verbatim in SVG and
JavaScript). `SkinName` must be ASCII letters and digits only (Zimbra drops
every other character from the skin parameter). A failed build leaves the
previous `skins/<SkinName>/` untouched.

## Making a variant

1. Copy `palettes/tide.properties` to `palettes/<name>.properties`. The tide
   palette lists every token, so it doubles as a template; the other palettes
   only list what they override.
2. Set `SkinName` (for example `blueshoreforest`) and change the colours.
3. Build, copy `skins/<SkinName>` to the server and install it as described
   in [INSTALL.md](../INSTALL.md).

Keep the shared typography and density: variants are colour-only by design,
which is what keeps the four skins in step with each other. If you want a
different density or typeface, change it once in `src/` and every variant
follows.

## Token reference

All tokens live in the `blueshore design tokens` block of
`src/blueshore/skin.properties`. Hex colours unless noted.

### Accent

| Token | Use |
|---|---|
| `AccentC` | accent fill: primary button, selection bar, unread dot, active-tab underline |
| `AccentHov`, `AccentAct` | hover / active states of the accent fill |
| `AccentTextC` | accent used as **text or stroke on a light surface**: links, active tab label, selected folder, counters, selected icons, checkmarks. Same as `AccentC` in the blue variants; in the amber ones it is a darker amber so that text stays legible |
| `AccentLightC` | light accent tint: avatar background, conversation-count badge, address bubbles, toasts |
| `AccentTintC` | mid accent tint: focus ring of the search box and address fields, selected-item outset borders |
| `OnAccentC` | text and glyphs **on** the accent fill. White in the light variants; in the dark ones the accent is light, so this is dark |
| `AccentShadowC` | shadow of the primary button (`rgba(...)`, passed through as-is) |

### Surfaces, borders, text

| Token | Use |
|---|---|
| `AppC` | application background (folder tree, panels); core name |
| `SurfaceC` | cards, menus, dialogs, list background |
| `TopbarC` | top band and app-tab row (white in the light variants) |
| `ReadPaneC` | reading pane / message header surface |
| `HoverC`, `ListHoverC`, `HeaderHoverC` | hover wash of tabs and widgets (also the search box background), list rows, section headers |
| `SelC` | selected row (core name) |
| `SelAltC` | selected row when the list does not have focus |
| `ConvExpandedC` | background of an expanded conversation in the message list |
| `BorderC`, `BtnBorderC`, `RowBorderC`, `SepLightC` | panel borders, button borders, list row separators, light separators |
| `TxtC` | default text (core name; also applied to `BODY`) |
| `TextHeadC`, `TextMidC`, `TextFaintC` | headings, secondary text and neutral icons, placeholders and faint text |

### Message body card

The body of a message is rendered as a light "card" even in the dark
variants, because HTML mail is designed for a white background.

| Token | Use |
|---|---|
| `MsgBodyBgC`, `MsgBodyTextC` | card background and text (also used inside the iframe of HTML mail) |
| `MsgCard` | box style of the card: empty/`padding` in light variants, margin + radius in dark ones |
| `PreviewCard`, `PreviewCardBox` | same treatment for the briefcase preview (radius; container padding). Empty in light variants |

### Status glyphs and tags

| Token | Use |
|---|---|
| `FlagC`, `FlagOffC` | flag set / flag not set |
| `ReadDotC` | dot of a read message (the unread dot uses the accent) |
| `PdfC` | PDF attachment icon |
| `TagBlueC` … `TagYellowC` (9) | the standard colours of folders, tags and calendars. Shared by every variant; also pushed into the client's colour table at runtime by `blueshore.js`, so coloured folder icons and tag pills use the same values |

### Native controls and legacy core tokens

| Token | Use |
|---|---|
| `ColorScheme` | `light` or `dark`: sets `color-scheme` on the document so the browser draws checkboxes, selects and scrollbars to match |
| `AppTabColorRGB` | RGB triplet used by the core for the app-tab row |
| `SkinAppRowColorRGB`, `SkinAppRowColorHex` | colour of the app row, as the core wants it (triplet and hex without `#`) |
| `PopupShadow` | shadow declaration of menus, dialogs and toasts |

Everything else in `skin.properties` (sizes, fonts, the core's component
definitions) is shared and derives from these tokens.

### Adding a token

When a new colour is needed in `skin.css` or in the icon generator:

1. add the token to the design-tokens block of `src/blueshore/skin.properties`
   with the tide value;
2. add the same line to `palettes/tide.properties` (the template) and to any
   palette that needs a different value;
3. reference it as `@TokenName@` in `skin.css` or `T("TokenName")` in
   `gen-icons.py`;
4. rebuild every variant.

## Dark variant checklist

The dark palettes are not an inversion: a few tokens carry semantics that
only show up on dark surfaces.

- `ColorScheme = dark`.
- `OnAccentC` dark: the accent is light on dark surfaces, white text on it
  would fail.
- `AccentTextC` slightly lighter than `AccentC` if the fill does not read as
  text on `AppC`.
- `MsgBodyBgC` white and `MsgBodyTextC` dark (the card), `MsgCard` with margin
  and radius, `PreviewCard`/`PreviewCardBox` set.
- `SelAltC` a muted version of `SelC`: the core default is a light grey.
- `TopbarC`, `ReadPaneC`, `SurfaceC`, `AppC` as three or four steps of the
  same dark neutral; `HoverC` one step above `SurfaceC`.
- `AppBannerImg` pointing to `AppBanner_white.png`: the Zimbra banner is
  monochrome, black on a light top bar and white on a dark one, as in the
  stock skins.
- After building, open Mail, Calendar (day/week/month), Tasks, Briefcase,
  Contacts, Preferences **and the compose / appointment / task forms**: those
  forms use native inputs whose white background is only overridden by the
  skin's global input rule.

## Icons

`tools/gen-icons.py` writes `icons.css` (one rule per Zimbra `Img*` class, SVG
data URI, colour from the tokens) and `img/images.css.js` (the image data the
client needs for avatar swaps and for the coloured folder/tag composites it
paints on a canvas). The mappings are plain dictionaries at the top of the
script: Zimbra class name → Lucide icon name (and colour role). To change or
add an icon:

1. drop the Lucide SVG into `tools/lucide/` (keep the file name);
2. add or edit the entry in the relevant dictionary (`FOLDERS`, `ACTIONS`,
   `PREF_PAGES`, …);
3. rebuild.

Two rules of the generator are not optional:

- hover/focus states are re-covered for every interactive icon, because the
  core has more specific `.ZHover .Img*` rules that would bring the legacy
  sprite back on mouse-over;
- `0%` inside data URIs is written as `0 %`: the server-side CSS minifier
  rewrites `0%` to `0` even inside URLs and corrupts the SVG.

If you add selectors to `skin.css`, test the CSS endpoint afterwards
(`curl -sk "https://mail.example.com/css/skin.css?skin=<SkinName>"` must
return 200): the server-side generator fails with HTTP 500 on some modern
selectors (for example `DIV[id$="x"]:has(...)`). Logic that needs the DOM
belongs in `blueshore.js`.

## blueshore.js

A small skin-local script loaded by the manifest, idempotent and driven by a
`MutationObserver`. It does five things CSS cannot: splits unread counts out
of the folder name into a badge, stretches the empty-state placeholder to
full height, swaps legacy avatar `<img>` sources with the SVG map generated in
`images.css.js`, re-aligns the "New" button menu to the button's right edge,
and applies the `Tag*C` palette to the client's colour table
(`ZmOrganizer.COLOR_VALUES`). It touches no core file and can be removed from
the manifest if you prefer a CSS-only skin.
